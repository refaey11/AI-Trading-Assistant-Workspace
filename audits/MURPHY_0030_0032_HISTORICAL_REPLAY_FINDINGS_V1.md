# Murphy 0030–0032 — Historical Replay Findings V1

Date: 2026-08-16
Branch: proposal/murphy-0030-box-policy-v1
Decision: BLOCKED

## Execution performed
A full local replay was executed against a 2,544-row GBPUSD D1 OHLC artifact extracted from the uploaded Workspace transfer. The extracted artifact is the project's `DMI_ADX_V1_OUTPUT/GBPUSD_D1_DMI_ADX_2016_2024.csv`; its OHLC rows run from 2016-01-03 through 2024-12-31 and contain 2,544 daily bars. The P&F engine used for the replay was reconstructed exactly from the current proposal-branch `pnf_3box_log_reference.py` implementation, including logarithmic box levels, 3-box reversal, and the documented deterministic bootstrap.

## Critical finding 1 — prior 89-column diagnostic is reproducible only with an evaluation-only reset
Using the proposed `0.6257356643%` box policy:

- Full 2016–2024 continuous build: **150 columns (75 X / 75 O)**.
- 2019–2024-only build: **89 columns (44 X / 45 O)**.
- 2019–2024 contains **1,609 bars**.

The project's previous backup reports 89 columns for 1,609 evaluation bars. That number is therefore reproducible when the P&F engine is re-bootstrapped at the start of 2019, not when the engine carries its P&F state forward from the 2016–2018 calibration/warm-up data.

This is a material methodology boundary. The project describes 2016–2018 as calibration/warm-up and 2019–2024 as evaluation, but the existing diagnostic count alone does not establish whether the P&F state should reset at 2019 or continue from the prior history.

## Critical finding 2 — sensitivity does not reproduce the historical diagnostic at 0.50%
On the 2019–2024-only build:

- 0.6257356643% -> **89 columns (44 X / 45 O)**
- 0.75% -> **71 columns (35 X / 36 O)**
- 1.00% -> **45 columns (22 X / 23 O)**
- 0.50% -> **bootstrap ambiguity at 2019-01-02** under the current deterministic ambiguity policy

The project backup previously reported 0.50% -> 137 columns. Therefore the prior 0.50% sensitivity result was generated by a different bootstrap/ambiguity implementation than the current proposal core. It cannot be imported as final evidence.

## Critical finding 3 — final evaluator cannot be frozen on these unresolved policy boundaries
The current rule contract requires a valid 3-box P&F construction and explicitly states that bootstrap and box-size policy must be approved before production evaluation. The project backup also states that the exact Tower volatility-to-box formula was not established and that the proposed percentage is a project operationalization only.

Therefore the replay can be used as a diagnostic, but it cannot be promoted to production PASS until governance explicitly chooses and freezes:

1. whether the P&F engine is continuous from the calibration/warm-up period into 2019–2024 or intentionally re-bootstrapped at the evaluation boundary;
2. the exact deterministic bootstrap/ambiguity policy;
3. the project box-size operationalization.

No profitability-based selection was used, and 2025 was not used.

## Availability / no-lookahead diagnostic
A prefix replay was executed for the 2019–2024 evaluation period using only completed bars through each evaluation timestamp. No replay exception occurred. At each 2019–2024 timestamp:

- 0030 structural origin evidence was available whenever an O column existed; in this run it was available on all 1,609 evaluation bars after the continuous/evaluation-specific construction was initialized.
- 0031 was available on 810 timestamps where the latest column was X with a previous O.
- 0032 was available on 799 timestamps where the latest column was O with a previous X.

This demonstrates implementation-level prefix availability for the current engine. It does **not** resolve the bootstrap/state-boundary policy discrepancy above.

## CI
The dedicated Murphy workflow exists, but GitHub reports no workflow run for the current proposal commits. Therefore CI remains unproven.

## Final decision
**BLOCKED**

Reason: the actual replay exposed a reproducibility/methodology discrepancy between the historical 89-column diagnostic and the continuous 2016–2024 construction, plus a 0.50% sensitivity discrepancy caused by bootstrap ambiguity handling. These are policy/evaluator-definition issues, not reasons to tune the result.

## Required next action
Do not tune the box percentage. Do not use 2025. First freeze the state-boundary and bootstrap policy at the project-governance level, then rerun the complete evaluator and sensitivity suite from that single declared policy. Only after that can the 2019–2024 result be classified PASS/FAIL and considered for freeze.
